# Repeated dependency/evidence study — preregistered procedure

The question is whether a larger, transitive maintenance task reveals useful workflow differences, not whether a limited prototype should already replace general-purpose languages. An independent Sherlock design session authored the business rules, fixtures and oracle; implementation/preflight is a separate Bob session. This is not an externally authored blind study.

## Before attempts

Freeze this procedure, protocol, full task/public starters and regressions, actual historical artifacts, mathematical cases, references/mutation controls, public tooling and grader code. Preflight proves the historical failure reproduces, the old input passes the still-faulty current baseline, a fresh regression still fails, both reference candidates pass all finite cases and all eight negative controls fail. Preserve the exact frozen bytes. Old pilot inputs/results remain unchanged.

Run three fresh configured-agent sessions per arm, paired/counterbalanced using the predeclared seed in protocol.json. No model/options override. Record actual exposed settings/usage or null. Repetitions share the same authored scenario; they are not six distinct maintenance tasks. Randomized order does not control all correlated model/familiarity effects. Pretrial amendment: unrestricted six-ID hash sorting happened to group all Wisp attempts first; before any attempts or frozen inputs, it was replaced with randomized pair order and alternating first arm. No seed or order was chosen using outcomes.

## Allowed trial inputs and outputs

Read only this procedure, the assigned arm's `public/starter.wisp` or `public/starter.ts`, `public/task.md`, `public/README.md`, `public/public-regressions.json`, the assigned arm's historical source/artifact/snapshot, and relevant public language/CLI/protocol documentation. Use ordinary search/full-source inspection, compiler-derived graph/context tools, real checking/execution and self-authored tests. No mandatory tool sequence or forced context budget. TypeScript gets strict tsc, BigInt, checker-resolved call/declaration/context navigation and a reproducible historical replay tool; it is not restricted to regex search or signatures.

Do not inspect `private/`, the maintenance grader/test implementation, other attempts, prior pilot solutions or parent conversation. Shared-checkout restrictions are instructional, not an access-control mechanism. Public tools import implementation modules but participants may invoke them without inspecting their source/private data. This is not a security-isolated holdout.

Each attempt writes only `evaluation/maintenance/submissions/ID/candidate.wisp` or `candidate.ts`, `decision.json`, and `evidence.md`. Self-authored scratch belongs under ignored `evaluation/work/maintenance-ID/`; do not modify supplied files, history, specifications or another attempt. No commits, pushes, new worktrees, dependencies, network or Docker. Submitted TypeScript has no host actions/imports and uses BigInt; the host test subprocess is not a security sandbox. The common change rule is **one or two existing parsed bodies**, with no outer-whitespace edits; `sample_*` functions and all other bytes stay fixed.

Aim for ten minutes per attempt; this is an instructional target, not an enforced agent deadline. Self-authored debugging is allowed. One final submission per cell; no parent code fixes or acceptance feedback before all finals are locked. Missing/failing submissions remain failures. Rerunning the same task with feedback would be a separate study.

## Decision schema and interpretation

Alongside the candidate, write:

```json
{
  "historical_input": "0",
  "historical_failure_reproduced": true,
  "current_old_input_passed": true,
  "old_replay_is_full_acceptance": false,
  "fresh_public_suite_passed": true,
  "explanation": "What was observed, what history does not establish, and the fresh checks actually run."
}
```

These are **participant assertions**, not authenticated tool telemetry. Report an unperformed or failed check as false, not a guessed success. Evidence.md records actual commands/outcomes, root cause and limitations. The scorer reports correctness/preservation separately from whether these structured assertions match the scenario. A correct JSON flag alone does not demonstrate understanding, actual execution, authenticity or user value. Logs are self-reports unless corroborated; full native-agent interaction/token records are not exposed here.

## Scoring and publication

Lock candidate/decision/log hashes before any final grading. Verify all frozen inputs on each scoring run. Actual Rust typed calls and strict TypeScript/Node execution compare every Decision field against 547 mathematical invocations; these may duplicate inputs and are not exhaustive. Ready/checking is not behavioral acceptance. Unknown/errors/missing/truncated results cannot pass. Protect historical artifacts and reproduce their recorded failure before interpreting current replay.

Record exact revisions, tool versions, grader/binary hashes and per-attempt outcome, preserving original reports. Host dispatch-window timing, when recorded, includes scheduling, tools and parent boundary overhead; it is not model-inference latency or a fair runtime benchmark. Tokens, peak context and verified model settings remain null unless genuinely exposed. Do not compare per-case Wisp process costs with batched TypeScript as agent efficiency.

Classify findings into missing capability, usability friction, and demonstrated design disadvantage. This fixture fits existing features and cannot evaluate missing modules, collections, richer data models or host integrations. No feature freeze is permanent and core network/filesystem restrictions are intentional: practical IO belongs in explicit host adapters, not arbitrary language execution. The decision after this study may be a targeted upgrade, a stronger trial, or a tooling-focused product—not a blanket usefulness/uselessness verdict from one scenario.
